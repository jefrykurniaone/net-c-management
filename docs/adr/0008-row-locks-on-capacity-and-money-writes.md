# A write whose refusal turns on a count takes `SELECT … FOR UPDATE` on the owning row, and everything that is not that row stays outside the transaction

Capacity and money are both decided by counting and then writing, and a count read in one statement and acted on in the next is a decision made against a state that no longer holds. `PATCH /api/sessions/[id]` once read the held-Seat count and wrote the new `maxPlayers` with nothing between them; a reservation committing in that window left `maxPlayers` one below the Seats actually held, which is the one invariant capacity has. Two Admins saving a Dues change at the same instant once both read "nothing queued", both inserted, and left two future rate rows that no disclosure can name and no Withdraw can reach. The fix in both cases is the same and this record states it once: the write takes `SELECT … FOR UPDATE` on the row that owns the thing being counted — the Session, the Activity — and does the counting and the writing inside one short transaction.

**The lock has to be the same row in the same statement shape as the path it races.** The reservation writes in `src/lib/payments.ts` (`registerAndPaySession`, `reserveSeat`) take the Session's own row lock, so `src/lib/session-writes.ts` takes that same lock and the two writes queue instead of interleave: whichever arrives second reads the other's committed count. `src/lib/dues-rate-writes.ts` does the same on the Activity before reading its rate rows. A lock taken on a different row, or a count taken outside the transaction and passed in, buys nothing.

**Everything the write does that is not counting or writing that row stays outside.** `releaseExpiredHolds()` is swept by the caller before the counts are taken, and stays outside because it is its own write with member email queued behind it. `auth()`, the dictionary, cache invalidation and every send are outside too. Production caps the connection pool at one connection per function instance (`src/lib/prisma.ts`), so a transaction that waited on anything but this row would be holding the only connection there is while it waited.

**A refusal is a returned value, never a throw.** The route answers a refusal with a 409; a refusal thrown from inside the transaction rolls it back and surfaces as a 500, which turns a correct decision into an error. The resolvers that produce those refusals are pure and live under `docs/adr/0005-pure-rule-modules.md`; the transaction consumes them.

**A freeze is judged by a clock read inside the transaction.** Where a write is refused because a Billing Period has arrived, `now` is read under the lock rather than passed in from the route, so the write is judged by the Period current when it actually happens rather than by the one the request started in. This is the one place in the codebase that deliberately reads a clock rather than taking it as a parameter, and it is not an exception to ADR 0005 so much as the reason that rule is about *rules* and not about writes.
