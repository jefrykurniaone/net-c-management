# The Register is the one seam every admin table draws through, and below `md` it collapses by axis rather than flattening into a card list

Six admin surfaces list rows at a desk, and six hand-rolled tables drift into six idioms — six header treatments, six empty states, six ideas about where a sort control goes. `src/components/admin/register.tsx` is the one seam they all draw through, and this record holds the four decisions that seam carries, so that the file itself can be read for what it draws rather than for why.

**A table inside a card, and the card is the object.** A `--card` face, `12px` radius, `shadow-lift`, and no border of its own — the treatment `DESIGN.md` gives every Rally card under *Shape and depth*. Inside it, in order: a header saying what the rows are and how many, the table itself edge to edge, and the pagination under a rule. Rows are ruled and columns are not. The ruled lattice that used to bound this component went with Papan Jadwal (ADR 0003), and it is not coming back as a grid of hairlines on a card face, because that is furniture the card already provides. The one rule under each row is drawn on the cells rather than on the `<tr>`, since a row border does not render while a table's borders are separate.

**Data, never nodes.** A caller describes columns and rows, and that is the whole interface. There is no `children`, no slot prop, no ordering prop and no per-cell class name, so a call site cannot reach in and restyle one cell into a second idiom — which is the failure the seam exists to prevent, and it would arrive one reasonable-looking exception at a time. Exactly two escapes exist and both are narrow: a per-column `render` in `register-columns.ts`, which decides the *value* a cell holds and nothing about the cell, and one control slot in `register-header.tsx` for the surface's primary action. Anything a surface wants beyond those two is a change to the seam, argued once, rather than a local override.

**The collapse is by axis, not by flattening.** At `md` and up this is a real `<table>`: `<th scope="col">` heads, native header association, one rule under each row. Below `md` the table's parts are set to `display: block`, each row stays a rule-bounded block inside the card, and its cells stack inside it under the column's own tracked-caps label. Two things it deliberately never becomes. It never becomes an unruled card list, because the rule is what still says where one record ends and the next begins once the columns are gone. And there is never a second DOM tree for the phone — one tree, restyled, so the two widths cannot drift apart in content, and so nothing has to be kept in sync by hand.

**Exactly one label source is live at any width, and nothing in the code enforces it.** Setting the table's parts to `display: block` drops the table role, and `<th scope>` association goes with it, so below `md` each cell has to carry its column's label as real text immediately before its value. That leaves two label sources in the markup at once, and they are switched by a complementary pair of class strings: the inline label is `md:hidden`, and the `<thead>` is `hidden md:table-header-group`. Exactly one is live at any width, so nothing is announced twice and the DOM order is the reading order at both. Nothing checks the pair. Edit one class string without the other and the register either announces every cell's column label twice at full width, or renders a phone list of bare values with no labels at all — both silent, both invisible to the type checker and to every test in this repository. That is why the file keeps a warning naming the two class strings where the argument used to be: this record is where the reasoning lives, and the file is where the person about to break it is standing.

This record decides nothing about which surfaces use the Register or what their columns are, and nothing about sort or pagination behaviour, which stay the controls every admin list page already uses.
