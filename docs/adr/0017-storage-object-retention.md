# A stored object lives exactly as long as the record that points at it, and a bucket holding one file per owner is cleared by owner, never as a bucket

Nothing in this product expires a stored file on a clock. A file is kept because a record points at it and removed because that record stopped pointing at it, and the four buckets `src/lib/supabase.ts` declares — `avatars`, `logos`, `payment-proofs`, `hero-images` — each get one answer to the same question and a different reason for it. **A member's replaced profile picture in `avatars` is removed on the next upload, and the driver is privacy**: it is a photograph of a face that the member has decided should no longer represent them, and leaving the predecessor retrievable is the defect, whatever it costs to store. **A `payment-proofs` object lives exactly as long as the Payment that carries it, and the driver is evidence**: giving up an unpaid Seat deletes the Payment and the Proof goes with it, while a Reviewed Payment's Proof is never touched — guaranteed by the existing refusal to delete a Reviewed Payment rather than by a second check here. **`logos` and `hero-images` keep exactly one object each, and the driver is tidiness**: an Admin who switches image format must not silently leave the old file beside the new one, which is what the filename extension makes happen. **Cost is a driver for none of the four.** If it were, the target would be `payment-proofs`, which is the one bucket that is supposed to grow; recording the drivers separately is what stops a later change reading one bucket's answer as the general one.

**The whole-bucket clear does not generalise, and this is the most important line in the record.** `hero-images` already implements the rule, and the pattern came from #155: `clearHeroImageObjects()` lists every object in the bucket and removes all of them before the new photograph is written, so accumulation is impossible regardless of filename or format. That is correct only because the bucket holds one meaningful file for the whole community. `logos` is the same shape and adopts it directly. `avatars` and `payment-proofs` are not that shape — every member owns files in one, every Payment owns a file in the other — and applying the unscoped clear to `avatars` would list the whole bucket and delete **every member's profile picture** on the next single upload, one member's replacement wiping the faces of everyone else. A per-owner bucket therefore lists and clears one owner's area, and a bucket-wide `list()` with no prefix is only ever correct where the bucket is a singleton.

**Failure behaviour splits by what the person asked for, and both halves live in one record so the next bucket does not re-decide.** A deliberate delete — an Admin removing the logo or the hero photograph, a member removing their picture — reports the failure. The person asked for the file to be gone, and telling them it is gone while it is still stored is the one outcome worse than the failure itself. A cleanup that runs *during a replace* swallows the failure and logs it. The new file is already stored, the request is what the person is waiting on, and a surviving predecessor is untidy rather than wrong, so failing the upload would trade the thing they asked for against a tidy-up they never asked for.

**A file's storage location is read before the record that holds it is deleted, and that order cannot be reversed**: once the record is gone, so is the only thing that knows where the object is, and no location can be derived from a public link the record no longer holds. So the location is read inside the transaction, carried out of it, and acted on after the commit — never inside, because storage is a third party that cannot participate in the transaction and because a removal that succeeded before a rollback would leave a surviving record pointing at evidence that no longer exists. Holding a money row's lock open across a third-party call is also exactly what `docs/adr/0008-row-locks-on-capacity-and-money-writes.md` exists to prevent. The residual failure — a crash between commit and removal — strands one object, which is the weaker of the two failures and is the condition a separate purge would cover.

**The decision of which objects go is a pure function; the call that removes them is not tested.** `selectSupersededObjectKeys` in `src/lib/storage-retention.ts` takes an owner's prefix, the names a listing returned and the key just written, and returns the keys to remove — no I/O, and nothing imported from the storage client, under `docs/adr/0005-pure-rule-modules.md`. It owns the join from a listing's relative name to a full key, because that mismatch is where a tidy-up becomes data loss: a bare `receipt.png` compared against a written `u1/receipt.png` differs as a string and would select the file that was just written. The removal call itself is deliberately uncovered — its failure mode is a network error rather than a wrong answer, and covering it would introduce the storage client as this repository's first test double and carry that double into every storage test afterwards. Behaviour that exists only at that boundary, a swallowed replace failure and a surfaced deliberate one, is verified by exercising the app.

**Two alternatives for `avatars` were rejected.** Storing the current picture's path on the `User` record and deleting that one path needs a schema change and can only ever clean up files uploaded after it ships, leaving every already-stranded file stranded permanently; clearing by owner collects a member's whole history the first time they upload again, with no migration. Naming the file after the member so each upload overwrites the last looks simpler, but the filename carries the image format, so a member switching format writes a second object and overwrites nothing — which is precisely the defect `logos` is sitting in today.

This record decides nothing about retention *periods*, of which there are none, and nothing about objects already stranded in production, which is real deletion against real data and its own decision. It does decide the default for the next bucket added: a singleton bucket inherits the `hero-images` answer, a per-owner bucket inherits the scoped one, and neither inherits the other's.
