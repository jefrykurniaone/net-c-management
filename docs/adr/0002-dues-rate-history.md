# A Dues Rate is a history of rows, not a live field and not a per-Period snapshot

An Activity's Dues Rate is stored as one row per (Activity, effective-from Billing Period), and the rate of a Period is the row with the greatest effective-from that is not after that Period. The two alternatives were a per-Period snapshot — one row per Activity per Period, written as each Period arrives — and keeping the live `monthlyFee` field with a rate history beside it as an audit log. The snapshot was rejected because it needs a writer that runs every month and must never miss: a Period that arrives while that job is down resolves to nothing, and "the price of this month" would depend on whether a cron succeeded rather than on what an Admin decided. The history needs no cron and no per-month write at all — a Period arriving changes nothing in the database, only what the resolver returns — and it answers a Period nobody has reached yet as readily as one long past. It also costs the product no new idiom: `Membership.paymentMode` / `pendingMode` / `pendingEffectiveFrom` already resolves a stored decision against a Period key, so Admins and code meet the same shape twice rather than two shapes once each. The price paid is that every read goes through a resolver over a row set instead of reading a column, which is one pure function (`src/lib/dues-rate.ts`) and one relation load.

**The earliest effective-from is the next Period.** An Admin may not set a rate for the current Period or any past one; the range is next Period through twelve Periods ahead. Allowing the current Period was rejected because it is precisely the defect being fixed: members who paid on the 5th and members who paid on the 20th would again be charged different figures for one month. Allowing a past Period — offered as a way to correct a mistake — was rejected because an arrived Period is settled: repricing January would make every January Payment retrospectively short or over depending on when the record is read, and there is no route by which a member could be told. A mistake in an arrived Period is handled as what it is, a Payment matter, not by rewriting what the month charged. The far bound of twelve Periods is a year, which is as far ahead as a committee decides and keeps the Period picker finite and the queued row meaningful.

**At most one queued change at a time.** Exactly one row per Activity may have an effective-from that has not arrived; saving a new rate replaces it and withdrawing deletes it, and neither ever touches a row whose Period has arrived. A schedule of several future changes was considered and rejected: the disclosure beneath the Dues field would become a list rather than a sentence, replace and withdraw would each have to name which future change they meant, and no user story asked for a second one. The uniqueness rule on (Activity, effective-from) is what makes replacing a queued change a single write on a known key rather than a delete-then-insert with a window in between.

**The live `monthlyFee` field is removed rather than kept as a cache of the current rate.** Keeping it would make the current figure cheap to read and cheap to sort the Activities register by, and it was rejected because two writable sources for one price is the defect this work exists to fix — the two would disagree the first time one write path forgot the other. Worse, a cache of "the current rate" is correct only until a Period boundary passes with nobody writing to it, and that boundary is exactly the moment its value must change, so it would need the monthly writer that the first decision above avoids: the cache reintroduces the cron through the back door. The register's value and its sort resolve through the rows instead. The removal follows expand–contract — the rows, the resolver and the seeding migration first, every read moved off the field next, the column dropped last with a build that carries no reference to it — so that at no point does a Period fail to resolve.

Two choices made while implementing the first step follow from the above and bind the rest. A beginning-of-time row seeded by the migration or by a seeder records `setById` as null: that amount is the Activity's standing price carried forward, not a decision an Admin took, and naming somebody would invent a decision nobody made — a row created through the Activity form does carry its Admin. And the resolver is a module free of `server-only`, Prisma and React, in the shape `src/lib/session-lock.ts` established, because the Admin's Period picker and the Proof upload form must answer "what does this month charge?" from the same rules the routes enforce, and a rule behind a server boundary gets copied rather than read. That required the Billing Period primitives — `BillingPeriod`, `toPeriodKey`, `currentPeriod`, `nextPeriod` and the beginning-of-time key — to move out of `src/lib/payment-mode.ts`, which imports `server-only`, into `src/lib/billing-period.ts`; `payment-mode.ts` re-exports them unchanged, so no existing import site was touched and `year * 100 + month` is still written in exactly one place.
