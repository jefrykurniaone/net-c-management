# A Membership's Payment Mode is a history of rows, not a standing field with a queued switch

A Membership records one standing Payment Mode with one effective-from Billing Period, plus one queued switch; when the queued switch arrives the standing moves onto it and what came before is gone. A settled Period therefore cannot be priced from the rows. For a Participant who was on Monthly through July and switched to Per-Session from August, `resolvePaymentMode` finds no selection covering March, falls back to the Activity's offered set, and on an Activity offering both modes answers `null` — so that Participant drops out of March's owed Dues although they owed them and very likely paid them, and March can read collected above owed. It is invisible on an Activity offering Monthly alone, because there the offered-set answer is right; it bites exactly where both modes are offered, which is what the seed and the product both treat as normal. `src/lib/dues-collection.ts` states the limit in full and `src/lib/__tests__/dues-collection.test.ts` pins it, so it is a known limit rather than a surprise regression. This record decides how it stops being one. It decides nothing else: no schema change, no migration, no backfill and no repointed call site lands with it.

**The shape is the one ADR 0002 gave the Dues Rate, and is not re-argued here.** One row per (Membership, effective-from Period); the row in force for a Period is the one with the greatest effective-from that is not after it; a beginning-of-time row at `BEGINNING_OF_TIME` so that every Period, however far back, resolves to a row rather than to nothing; and a uniqueness rule on the pair, which is also the index every read uses. The two alternatives — a per-Period snapshot written as each Period arrives, and keeping the live fields with a history beside them as an audit log — were weighed and rejected in `docs/adr/0002-dues-rate-history.md` for reasons that hold here word for word: a snapshot needs a writer that runs every month and must never miss, so "what Payment Mode was this Membership on" would depend on whether a job succeeded rather than on what a Member decided; and two writable sources for one fact disagree the first time a write path forgets one. What this record settles is what the rows are made to say, not what shape they take.

The table is named `MembershipPaymentMode`. `MembershipMode` is already the name of the resolver's input interface in `src/lib/payment-mode.ts` and is the name Prisma would generate for the model, and the same care that named `ActivitySession` rather than `Session` applies to a collision inside one file. It mirrors `DuesRate` field for field — `effectiveFrom Int`, `setById String?` with `onDelete: SetNull` because a row outlives the person who wrote it, `setAt DateTime @default(now())`, `membershipId` with `onDelete: Cascade`, and `@@unique([membershipId, effectiveFrom])` — with two deliberate differences, each stated as a difference rather than left to be noticed. `mode` is `PaymentMode?` where `DuesRate.amount` is not null: an Activity always charges something, but a Membership genuinely can have chosen nothing, and that unselected state — which `Membership.paymentMode` already spells as null on an Activity offering both modes — must survive into the rows rather than be flattened into a guess. And `setById` names the Member who chose rather than the Admin who set a price, because a Payment Mode is the Participant's own decision; it is null on any row no person decided, which is a row written by the migration, by a seeder, or by the join-on-register path that auto-applies the sole mode an Activity offers.

**The backfill asserts only what a column already records, and records the unrecorded as unrecorded.** Per Membership it writes: a beginning-of-time row at `BEGINNING_OF_TIME` carrying no mode; a row at the Period of `joinedAt` marking the Membership present from then; a row at `effectiveFrom` carrying `paymentMode` where that is not null; and a row at `pendingEffectiveFrom` carrying `pendingMode` where a switch is queued. Facts landing on one Period are one row, not two — presence and mode are separate columns of the same row precisely so that this is a merge rather than a conflict with the uniqueness rule — and every value written is copied from a column that already holds it. Nothing else is asserted. Before the earliest recorded selection the rows say only that no selection is recorded, which is true, and which resolves the way it resolves today: where the Activity offers a single mode that mode still applies, because auto-applying the only mode on offer is a rule (FR-9, FR-10) and not an inference, and where both modes are offered the answer stays `null`. The backfill therefore changes no figure that is right today; it changes an unanswerable Period from silently absent to explicitly unrecorded.

The alternatives were three. *Writing today's standing at the beginning of time* — one row per Membership at `BEGINNING_OF_TIME` carrying `paymentMode` — was rejected because it is the current defect performed deliberately: it asserts that a Participant who switched to Per-Session in August was on Per-Session in March, which is the direction the bug already errs in, and it launders that guess into a row that ADR 0002's own rule then freezes forever, since a Period that has arrived is settled and its row is never rewritten. It is worse than the defect it replaces, because today the loss is visible as a Period reading collected above owed, and afterwards the figures would look plausible and the loss would be undiscoverable. *Inferring the past mode from Payments* — a Period carrying a Confirmed Dues Payment implies Monthly — was rejected because `src/lib/payment-mode.ts` states the rule the whole product rests on, that the mode is never inferred from past payments (AD-7), and a migration doing it once is that same inference with a different author. The evidence also runs the wrong way: a Participant on Monthly who never paid March has no Dues Payment for March, so the inference would read them as Per-Session, and the backfill would quietly cancel the arrears of exactly the people who owe them. *No backfill at all*, leaving the table empty and the resolver falling off the end of the rows for any Period nothing covers, was rejected because the beginning-of-time row is what makes the resolver total: without it "no row" and "a row saying nothing is recorded" are indistinguishable, and every consumer keeps a second code path for a case the rows could simply state.

Two limits of the backfill are recorded here rather than discovered later. A Membership that is already inactive when the migration runs gets no presence row, because no column records when it ended and inventing that date is the same guessing this record forbids; those Memberships stay excluded from every Period, exactly as they are today. This is a one-off loss confined to departures that happened before the migration, and it does not grow, because every departure after it is dated by the decision below. And `joinedAt` is the first join and is not rewritten when a Membership is re-joined, so for a Member who left and came back the presence row copied from it claims a gap they were absent for — which is what `monthlyMemberCount` reads today. Carrying that reading across unchanged is deliberate: `joinedAt` is the only recorded fact about presence, and manufacturing a gap would be inventing history as surely as erasing one. Rows written after the migration record such a gap correctly.

**Deactivation gets a recorded end, and it is recorded as a row in this history rather than as a column on `Membership`.** Leaving an Activity writes a row at the Period the departure takes effect from, marking the Membership no longer present; re-joining writes another row marking it present again. One row set, one resolution rule, and a Member's spells of participation come out of it for free: "was this Membership priced in this Period?" is answered by the same greatest-effective-from-not-after row that answers "on which Payment Mode?", because presence and mode are two columns of one row. The row carries `isParticipant Boolean` beside the nullable `mode`, and the two are kept apart on purpose. Not being a Participant in a Period and having recorded no selection in it are different facts — the distinction ADR 0001 drew between Opted Out and No-Show, and the glossary draws between Admit / Decline and Confirm / Reject — and collapsing them into one nullable column would make a departed Member and an undecided one the same row.

*A timestamp column on `Membership`* — `endedAt` beside `joinedAt`, nulled on re-join — was rejected because `@@unique([userId, activityId])` means one Membership row per (User, Activity) forever and `ensureMembership` reuses it, so a second spell overwrites the first one's end and the gap between them becomes indistinguishable from continuous presence: the very class of loss this record exists to end, reintroduced in a new column. A timestamp also answers "when" where every question here is asked about a Period. *Adding a third value to the `PaymentMode` enum* to mean "gone" was rejected because eighteen sites ask the resolver for a mode and nearly every one of them branches on a single value against everything else, so a third value would make each of those branches silently right or silently wrong without a compiler ever asking; ADR 0001 added a fourth attendance value precisely because it could be kept out of the pairs that already had meaning, and this one could not. *Recording nothing, and keeping departed Members out of every Period* was rejected because it leaves half the reported defect standing, and it is the half that grows: every Member who ever leaves permanently removes owed Dues from every settled Period they were present in, so the community's collection rate improves the more people leave it. `Membership.isActive` stays where it is and keeps its job, which is gating what a Member may do now; the history answers what a settled Period should have charged. The departure row and the `isActive` write happen in one transaction so the two can never disagree, and whether the flag is later derived from the rows is left to the run that builds this, since it is read by guards that have nothing to do with money.

**The queued switch becomes the act of writing the next history row, and `pendingMode` / `pendingEffectiveFrom` are removed.** Setting a switch for a future Period writes a row at that Period; withdrawing it deletes that row; re-picking the standing mode is a withdrawal. "At most one queued change" survives unchanged as ADR 0002 already states it for the Dues Rate: at most one row per Membership whose effective-from has not arrived, replaced on a known key rather than deleted and re-inserted with a window in between, and no write ever touching a row whose Period has arrived — which turns current-Period immutability (AD-7) from a branch somebody must remember into a property of the table. It also retires `graduateStanding` and the hazard its comment describes: today an elapsed queued switch is folded in at read time and never persisted, so any write path comparing against the raw fields instead would rewrite an already-effective Period, and every future write path has to know that. With the switch stored as a row at its own Period there is nothing to graduate, and that bug becomes unrepresentable rather than guarded against.

*Keeping the pending pair as it is, with history rows written only when a switch lands*, was rejected because the landing needs a writer: either a monthly job — the same cron ADR 0002 rejected for the snapshot — or a lazy write on the Membership's next update, which leaves a Membership nobody touches for a year with no row for any Period its switch covered, so a read would have to consult the rows and the pending pair both, and the answer for a settled Period would depend on whether somebody happened to write since. *Keeping the pending pair as a cache of the next row*, for the disclosure sentence a Member reads beneath the control, was rejected for the reason ADR 0002 removed `monthlyFee`: two writable sources for one fact disagree the first time one write path forgets the other, and the queued row is already cheap to find from the rows — the earliest effective-from after the Period, which `findQueuedDuesRate` does for rates and `src/lib/membership-mode-view.ts` can do the same way. *Allowing a schedule of several queued switches* was rejected as ADR 0002 rejected it — the disclosure becomes a list rather than a sentence, replace and withdraw would each have to name which future change they meant, and no user story asked for a second one — and for one reason of its own: whether a switch takes effect this Period or the next is gated on whether the Member has a live Payment for it, and that gate cannot be evaluated for a Period that has not arrived.

**What follows, and what does not.** Nothing in this record is built by the run that writes it: there is no schema change, no migration, no backfill and no repointed call site, and the standing fields keep working exactly as they do. The run that builds it adds the model and one migration that creates the table and writes the backfill rows in the same migration — as `20260829163748_add_dues_rate` did, so that no Membership exists for even a moment without a covering row — then moves the resolution onto the rows behind the existing `resolvePaymentMode` name, then removes `pendingMode` / `pendingEffectiveFrom` last, in the expand–contract order ADR 0002 used for `monthlyFee`, so that no Period ever fails to resolve in between. Three consumers will read the history: `resolvePaymentMode` in `src/lib/payment-mode.ts`, the seam every other consumer goes through, whose signature is untouched by this record and which is called from eighteen sites across `src/` (measured, not estimated); `monthlyMemberCount` in `src/lib/dues-collection.ts`, whose documented limit and pinned test are removed only when the rows can actually answer, never before; and the admin dashboard's owed total (#203), which reaches the rule through `monthlyMemberCount` rather than restating it. One question is deliberately left open for that run: `resolveDuesRate` lives in a module free of `server-only` so a client control can read the same rule the route enforces, and whether the mode resolver needs to move the same way depends on which surfaces end up asking, which nothing here needs to decide.
